# 0.42.3 성능 최적화 검증

> 이 문서의 기존 표·223파일 manifest는 이전 후보 d7f41a28/84f22666 및 baseline 881fd7c9의 Windows 측정이다. 아래 수치를 최신 main 결합 결과로 재사용하지 않는다.

## 클라우드 재개 및 기본 화면 우회 보완 (2026-10-26)

- 최신 main `9de45fda80bac1cf920732ce22024261ac5f2f0e`의 RAF 종료 수명 수정을 결합했다.
- 자동 카메라와 전체 지면이 보이는 수동 overview에서는 per-unit visibility 검사와 visible 목록 작성을 건너뛰고 기존 shadow/ring/actor 정렬/draw 흐름을 사용한다. 사용자가 확대/패닝으로 전장을 자른 경우만 컬링한다.
- 수동 컬링의 숨은 actor 정렬 위치와 vector→mesh flush, 숨은 clip 전환, 활성 무기 궤적·옥수수 부착 예외를 유지한다. 효과 컬링과 HP 합산 이동은 도입하지 않는다.
- 기존 기본 화면 500명 측정에서 라운드 평균 median 31.35→36.75ms(+17.2%), p95 46.35→63.85ms가 관찰됐다. 첫 라운드 워밍업/순서 영향 가능성은 원인 확정이 아니며 이 결과를 삭제하거나 최신 보완의 통과 증거로 취급하지 않는다. 기존 전체 UI 100 안정 mean +2.08ms, 500 안정 +0.62ms 경고도 유효한 과거 기록이다.
- 새 CI는 Linux의 같은 Chromium 프로세스에서 최신 main→결합 후보의 기본/수동 화면을 각각 양순서로 비교한다. seed731, 500전열+500예비대, 20TPS, 동일 96frame 워밍업과 80표본을 사용하고 워밍업 원시 시간도 보존한다. source hashes와 정확한 후보 head는 새 `performance-cloud` artifact에 포함한다.
- 기존 150프레임 픽셀/시계 비교에 자동→수동 확대/패닝→reset 12프레임을 추가한다. `npm test`의 pagehide/reload와 HUD 테스트도 결합 head에서 실행한다.
- dot 클라우드의 로컬 Node 정적/경계 테스트는 실행 가능하지만 Chromium은 sandbox socket 제한 및 승인 실행의 환경 준비 오류로 시작하지 못했다. 브라우저 결과는 기존 GitHub Actions에서 실행한 exact-head 결과로만 판정한다. 이 절의 CI 결과는 아직 진행 전이며 성능/FPS 향상 또는 회귀 없음의 확정 주장이 아니다.

기준은 `881fd7c9b97efc00ca2e2a46c1ee5b069f7ccdfe` (0.42.2), 최초 검토 head는
`09bf8f07effe582d79809ba23d9d95efb375b3e3`이다. 기존 사용자 체크아웃과 미추적 테스트
산출물은 건드리지 않고 별도 복제본/브랜치에서 작업했다. 기준 Git tree와 사용자
체크아웃에는 `.agents/skills`가 없었다.

[공통 개발 규칙](https://github.com/byh-playground/bloom-reference/blob/main/rules/development.html)과
[알고리즘 레퍼런스](https://github.com/byh-playground/bloom-reference/blob/main/algorithms/index.html)의
실제 내용을 읽고 SSOT/Signal 소유권, A071, A078/A038, 호출 수×단위 비용 및 상태 동등성 기준을 적용했다.

## 변경과 안전 경계

- 렌더: 실제 native mesh 정점·morph·파트 부모 계층·clip keyframe의 보수적 경계를 자산별로
  한 번 계산한다. 지상 그림자/링과 공중 몸체, 최소 픽셀 크기·거대화·외부 공격 포즈·잠듦 표시를
  합집합으로 검사한다. 화면 밖에서는 pose 평가·seek·그림자·등급 링·몸체 제출을 생략한다.
  가벼운 actor는 기존 정렬 위치에 유지하고 native mesh flush 순서를 보존한다.
  `prepareUnits`, 살아 있는 ID 관리, player clip/expression 전환은 계속 관찰한다.
  합성 연출이 원래 숨기던 병력의 시계는 갱신하지 않고, 비활성 무기 궤적은 정리한다.
- 큰 보스, 투사체, 옥수수 부착 대상, 활성 벼/밀/보리 무기 궤적, 보리 상태 텍스트,
  알 수 없는 아트 형식과 모든 효과는 계속 그린다. 이 항목의 렌더 감소를 주장하지 않는다.
  효과 컬링은 독립적인 이득과 native flush 순서 보장이 부족하여 철회했다.
  시뮬레이션 roster/step은 바꾸지 않았다.
- UI: 인구는 기존 collection revision, 손패/전선은 membership·bench·health·progress·tick을
  이용해 재사용한다. 명령 HUD와 손패가 하나의 hand query 결과를 읽는다. 전체 인구,
  field, bench, player, summon/clone의 기존 포함 조건을 각각 보존한다.
  HP는 기존처럼 매 표시 프레임의 `display.units`를 순회한다. tick 캐시하지 않는다.
  실제 HP 보간과 maxHp/death/revival의 경계 처리를 유지한다.
- 충돌: 매 impulse/Jacobi 조회에서 현재 위치·높이와 제곱거리로 기여하지 않는 후보만
  정렬 전에 제외한다. 경계 오차에 여유를 주고 남은 쌍은 기존 순서와 `Math.hypot` 판정을
  사용한다. 기존 몸체 캐시를 impulse와 solver가 공유한다. impulse가 바꾸는
  velocity/stun/flash는 몸체 반경·높이·질량 getter에 영향을 주지 않는다.
  후보 목록을 다음 패스에 재사용하지 않는다. sparse grid는 유지했고 옛 battleContacts,
  SAP, SoA, GPU 인스턴싱으로 교체하지 않았다.

## 환경과 프로토콜

사용자 Windows PC의 Intel Core i7-9750H, Node v25.9.0에서 모델을 별도로 측정했다.
브라우저 검증은 같은 PC의 Playwright Chromium **153.0.8010.12 / SwiftShader**이다.
물리 모바일 기기 FPS, 하드웨어 GPU 완료 시간, GC pause를 측정한 결과는 아니다.
화면 제출 CPU와 모델 tick, 표시 프레임+UI 비용을 구분한다.

seed 731, 20TPS, 혼합 9종 T1, 전열 100/250/500과 같은 수의 예비대를 사용한다.
최대 사례는 총 1,000 보유/500 예비대다. 내구성이 큰 저공격 보스로 전투를 유지한다.
초기 밀집과 120tick 이후 안정 구간을 따로 기록하고, 전후 순서를 교대한다.
계수 instrumentation과 snapshot 직렬화는 CPU 시간 측정 밖에서 수행한다.

Node 측정 초기 아카이브는 Windows CRLF였다. 해당 raw source hash는 원보고서에 보존했다.
Git blob과 줄바꿈만 다름을 확인했고, 브라우저 측정 전 `core.autocrlf=false`로 다시 archive하여
원본 Git 바이트를 검사했다. 이후 자산과 소스 pin을 완화하지 않았다.
PR359의 13/56ms나 PR360 CI의 35/103ms와 이 수치를 회귀 배율로 비교하지 않는다.

## UI 집계와 채택하지 않은 변경

손패를 그리는 UI와 명령 HUD는 같은 native hand query 결과를 공유한다. 60회의 UI
갱신에서 앱의 `handCounts`는 120→20회, 500 예비대 순회는 60,000→10,000개가 됐다.
모델 tick이 자체적으로 호출하는 20회는 그대로이므로 전체 호출은 140→40회다.
`handCounts`마다 만드는 Map도 앱 경로에서 100개 줄지만 전체 힙 할당량이나 GC pause는
측정하지 않았다. 인구는 같은 collection revision에서 다시 순회하지 않는다.

처음 검토 head `09bf8f07`의 HP 합산을 표시 모델 수집 순회로 옮긴 변경은 채택하지
않았다. 표시+sync 전체 평균 비용이 250명 안정 구간의 두 라운드에서 각각 약
11.0%, 12.7% 증가했고, 500명 안정 구간은 거의 같았다. sync만의 시간 감소로
이득을 주장하지 않고 기존 표시 HP 순회를 복원했다. 손패/인구 캐시만 남긴 후보를
별도로 재측정했다. 원본 결과는 `performance-optimizations-fusion-complete`에 보존했다.

전체 시간의 이득은 일관되지 않는다. 같은 baseline의 절대 시간도 실행 사이에 달라졌고,
100/500 안정 구간은 악화됐다. 이 결과를 숨기거나 전체 UI가 빨라졌다고 주장하지 않는다.
이 변경에서 확인한 이득은 native 쿼리·Map 생성·예비대 순회의 감소이며, 상태 동등성과
즉시 갱신을 검증했다. GC pause나 전체 프레임 성능의 개선은 미검증이다.

## 동등성·경계 검증

- Node 6개 규모/명령 사례의 216개 권위 상태 체크포인트, 모든 공격/피해 notice,
  산개 공격 순환 hash가 동일했다.
- 100/250/500 전열에서 죽음·증원·분열 2개·복제·층 보상·층 전환과 중간 snapshot
  복원 후 40tick의 상태가 일치했다. 배열 순서는 보존하고 객체 키만 정렬하는
  canonical hash와 deep equality를 함께 검사한다. 최초 raw JSON 해시의 실패는
  옥수수 payload 객체 키 삽입 순서 차이였으며 assertion을 유지한 채 직렬화만 바로잡았다.
- 접선·높이 경계·동일 위치·거대화·고정 몸체·후속 Jacobi 패스의 새 접촉을 검증했다.
- HUD 100/250/500 전열과 예비대, 동일 tick 사망·부활·증원·복제·삭제·최대 HP·재정렬·
  restore/reset·구독 해제 및 읽기 전후 snapshot 불변을 검사했다. native HP 보간과 실제
  DOM의 체력 수치·폭·문구는 별도 브라우저의 15개 상태·75개 보간 샘플에서 일치했다.
- 9종의 실제 native pose 2,114개, 정점 3,518,814개와 세 morph 끝점이 경계 안에 있었다.
- desktop 1280×800, portrait 390×844, landscape 844×390에서 각 50개, 총 150개
  전후 WebGL 픽셀이 정확히 일치했다. 기본/수동 줌·패닝, 네 화면 경계, 도약/지상 그림자,
  거대화·복제·잠듦·옥수수·무기·효과·투사체를 포함했다. 유닛 좌표를 고정하고 카메라만
  화면 밖으로 옮겨 idle→walk→idle 및 전체 공격을 진행한 뒤 복귀했을 때 clip,
  player identity, animation time, body pose도 같았다.
  같은 종·expression·모든 part pose의 visible→hidden→hidden 연속과 실제 앞/뒤
  표식을 추가해, 27개 중 9개만 그릴 때도 native mesh 배치 경계의 픽셀을 검사했다.
- 확장 전장·보스 3마리의 250명 벽/500명 모서리 사례는 각각 20tick 돌격 후 60tick
  퇴각했다. 모든 tick의 상태·notice·기여쌍 순서가 일치했다. 후속 Jacobi 새 접촉
  1,542/6,488개와 벽 충돌 24,062/55,797회도 같았고, 정렬 후보만
  2,189,479→472,441 / 22,382,043→6,122,562로 감소했다.
- 화면 밖 전투 통합 검증은 100/250/500명 각각 40tick·2회 비교했다. 그리기가 생략된
  프레임에서 공격 17/30/54회, 피해 17/32/49회가 실제 발생했고 권위 상태·notice·
  체크포인트·순환 hash가 같았다.

첫 CI의 가로 수동 카메라/벽 산개 검사는 `actors >= 100`과 전체 유닛 draw 수를
요구하여 실패했다. 같은 renderer/player/snapshot/camera의 컬링 켬/끔 전체 픽셀
대조로 교체했다. 기본 화면/산개 비교에는 실제 병력 아트의 픽셀 기여도 검사를 추가했고,
기존 제스처·카메라·권위 상태·산개/공격 검증은 유지했다. PR362의 탭 종료 수명주기
조사는 별도 범위이며 이 변경에서 프레임 종료 정책은 수정하지 않는다.

강화한 벽 산개 검사는 5초 시점에 4픽셀 차이를 추가로 검출했다. 서로 다른 화면 밖
유닛 11개 중 하나의 native mesh flush만 되살려도 차이가 없어져, 아트 경계 누락이
아닌 제출 순서 문제임을 분리 확인했다. 숨긴 actor를 원래 정렬 위치에 유지하고
`vector.flush` 후 `meshes.flush`를 실행하여 해결했다. 전체 context flush는 primitive를
먼저 제출하므로 대체하지 않는다. actor 정렬 감소는 철회했다. 수정 후 벽 산개 5장면과
가로 카메라 4장면, 위 150프레임을 모두 다시 비교하여 0픽셀 차이를 확인했다.

## 재현 명령

baseline은 위 기준 SHA의 `git archive`를 별도 디렉터리에 푼 원본이어야 한다.
각 성능 사례를 별도 프로세스로 실행하고 다른 부하와 겹치지 않게 한다.

```sh
npm run check

npm run test:render-bounds
node tests/contact-performance.test.mjs ../baseline 500 engage
node tests/contact-lifecycle.test.mjs ../baseline 500
npm run test:contact-boundaries -- ../baseline 500 corner
npm run test:render-visibility -- desktop
BUDMORI_PERF_BASE_ROOT=../baseline npm run test:performance-optimizations -- render 500 settled offscreen
BUDMORI_PERF_BASE_ROOT=../baseline npm run test:performance-optimizations -- hidden 500 settled offscreen
```

`tests/output/contact-performance/`, `tests/output/render-visibility/`,
`tests/output/performance-optimizations/`에 raw 표본·해시·브라우저 정보·PNG를 보존한다.

기존 소스 부팅·탑 병력·카메라·산개 회귀에 추가하여 실행한다.

ZIP 내부 경로는 저장소 상대 경로이며 요약의 SHA256으로 원본을 검사할 수 있다.
