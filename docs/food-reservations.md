# 먹이 예약과 검증

새싹이 먹이를 얻기 전에 성체가 먼저 먹는 상황을 줄이기 위해, 배고픈 주민마다 서로 다른 근처 먹이 하나를 예약한다. 기존 먹이 생성량·이동 속도·식사 후 대기·번식·3회 식사 성장 규칙은 유지한다. 성장 크기·카드·합류 연출 후보는 이 변경에 포함하지 않는다.

## 소유권과 수명

- `features/farm-modes/food-reservations/model.js`의 `FoodReservations`가 Garden당 하나 존재한다. 기존 UnitCollection과 food 배열의 객체를 빌려 `byUnit`, `byFood` 양방향으로 연결한다. 객체를 복제하거나 영구 ID를 추가하지 않는다.
- 새싹 검색 큐를 먼저 처리하고, 각 큐 안에서는 한 작업씩 순환한다. 이미 유효한 예약은 더 가까운 먹이가 생겨도 유지한다. 성체가 이미 예약한 먹이를 새싹이 빼앗지는 않는다.
- 최종 예약 직전에 소유자·먹이 유효성과 현재 거리를 다시 검사한다. 타인의 예약 먹이는 다른 주민과 소유자 없는 직접 소비 모두 거절한다.
- 소비·검색 취소·주민 제거/사망·일꾼 전환·합성 시작·성장·씬 전환 때 해제한다. 예약 목록은 매 틱 검사하며 2.5초 동안 0.08m 이상 가까워지지 못하거나, 총 8초가 지나면 해제한다. 원거리 예약은 이동 속도 기준 6초 거리 이내로 제한한다.
- 예약 수명 검사 비용은 예약 수에 비례한다. 주민마다 전체 먹이를 다시 훑지 않는다. 새싹 우선은 현재 검색 대기열의 순서이며, 무한한 새싹 유입 아래 성체의 무조건적 완료를 증명하는 정책은 아니다.

## 탐색 예산과 공간 인덱스

기존 고정 공간 그리드와 링/버킷 탐색을 재사용한다. 링 면적이 먹이 수보다 커지면 기존과 같은 제한적 fallback을 사용한다. 후보 검사 1회 또는 셀 방문 1회가 1작업이며 SDK scheduler의 **틱당 24작업, quantum 1**은 그대로다. 무효 작업 폐기·빈 검색 완료도 최소 1작업으로 계산한다. 예약 목록 검사·큐 관리·인덱스 재구성은 이 검색 작업 수에 포함하지 않으며, 이 지표를 전체 CPU 비용으로 해석하면 안 된다.

SDK에 검색 큐 export API가 없어 하나의 broker 작업이 새싹/성체 큐를 소유한다. 처리 도중 새 작업을 추가해도 현재 상태의 커서와 순서를 보존한다. 미예약 먹이가 없으면 새 검색을 만들지 않는다. 빈 결과는 먹이 인덱스 revision, 주민의 1m 이동, 또는 **해제 전용 availabilityRevision**이 바뀔 때 다시 검색한다. 다른 주민의 예약만으로 빈 검색 전체를 재시작하지 않는다. 이 최적화는 검사 비용 증가를 없애거나 처리량을 높였다는 결과는 아니다.

## 내부 rollback과 디스크 저장

`foodRuntime`은 내부 `farm-state` 체크포인트 전용이다. 예약 시간·진행 거리, 양방향 소유권, 두 큐의 순서, 검색 상태와 링/버킷/fallback 중간 커서, 사용 중인 과거/현재 공간 스냅샷, 인덱스 revision을 함께 저장한다. 소비 직후 아직 재구성 전인 배열 슬롯은 `null` tombstone으로 보존한다. 이 슬롯을 압축하면 다음 틱의 인덱스 revision과 검색 결과가 달라지므로 복원 시에도 유지한다. 큐 중복·먹이 인덱스 오류·과도한 커서·셀 내 중복은 거절한다. 이전 내부 스냅샷은 `foodRuntime: null`로 이행한다.

일반 디스크 저장의 SSOT인 `farm-progress.js`는 변경하지 않는다. 저장되는 것은 주민/새싹 식사 진행·대기와 먹이 수이며, 재접속할 때 실시간 위치·예약·검색 커서는 복원하지 않는다. 내부 rollback과 재접속을 같은 계약으로 취급하지 않는다.

## 재현 명령과 회귀

```sh
npm run test:food-reservations
node tests/food-reservations.e2e.mjs --bench --liveness --fixed-supply
```

첫 명령은 실제 Garden과 로컬 pinned SDK를 Chromium에서 실행하며 renderer/RAF 없이 예약·실제 식사·3회 성장·사망/합성/씬 해제·정체/원거리·디스크 복원·중간 커서 rollback을 검사한다. 220명 검색 중 복원한 전체 상태를 180틱 비교하고 잘못된 체크포인트 거절도 검사한다. core CI에는 이 기능 검사만 추가하며 벤치는 넣지 않는다.

비교 벤치는 immutable 기준 커밋 `0233b71335eacbaae2a0921ae758d40a40c4bc5f`의 먹이 탐색 owner를 사용한다. 다른 모델 규칙과 최초 전체 스냅샷은 동일함을 assert한다. 기준 파일 SHA와 후보 파일 SHA, 실행 환경을 원시 JSON에 기록한다. 완전한 과거 앱 빌드 비교가 아니라 **동일 모델에서 탐색 owner를 교체한 비교**다.

동일 seed 424242, dt 0.05초, 성체 200명+새싹 20명, 실제 정원 220명, 일꾼 0명, 창고 50개, 동일 위치 격자를 사용한다. 정원 포화로 기존 규칙에 따라 출산이 막혀 성체는 첫 식사 후 반복 소모하지 않는다. 먹이는 실제 비행/착지 경로로 일반 초당 10회·부족 초당 2회 생성 시도한다. 창고가 차면 시도가 거절되므로 **시도 수와 실제 생성 수를 구분**한다. 이동 속도 입력 3.6에 기질 배율이 적용되고 새싹 식사 대기는 5초다.

## 관측 결과와 한계

원시 자료는 `docs/benchmarks/food-reservations-fixed-180.json`과 `food-reservations-original-90.json`에 보존한다. 최초 90초 전원 식사 기준은 후보와 기준 모두 달성하지 못했다. 이 실패를 삭제하거나 통과로 바꾸지 않았고, 같은 공급 시도와 시작 조건을 180초까지 관측해 이 fixture에서 기아가 해소되는지를 별도로 확인했다.

최초 실패 JSON의 `HEAD`는 당시 `765eb219bce148d2e89cbda6e1667cecb0e434ad`다. 이 기준과 최종 고정 커밋의 먹이 탐색 파일 SHA-256은 모두 `5b46010b7f231595ba8d8ee59e2ebe280326a564281f1017e15de7976be3c257`로 같다. 과거 원시 기록은 그대로 두고, 현재 재현 명령은 위 immutable 커밋만 참조한다.

| 180초 고정 관측                    | 기존 일반 | 예약 일반 | 기존 부족 | 예약 부족 |
| ---------------------------------- | --------: | --------: | --------: | --------: |
| 새싹 20명 마지막 성장(초)          |    122.25 |     23.60 |    149.75 |     37.40 |
| 원래 성체 200명 마지막 첫 식사(초) |    117.90 |    120.35 |    140.40 |    149.20 |
| 총소비                             |       280 |       280 |       280 |       280 |
| 후보 검사                          |    14,749 |    14,841 |    18,442 |    21,349 |
| 셀 방문                            |    38,397 |    38,649 |    38,387 |    39,652 |
| 합계 검색 작업                     |    53,146 |    53,490 |    56,829 |    66,581 |

일반 공급 시도 1,800회, 부족 공급 시도 360회이며 모두 실제 330개 생성·280개 소비·50개 잔여다. 280개는 원래 성체 200식사+새싹 성장 60식사+성장한 20명의 첫 성체 식사다. **총처리량은 모두 초당 1.56개로 같으며 증가하지 않았다.** 새싹 성장 완료는 빨라졌고 성체 마지막 식사는 일반 2.45초·부족 8.8초 늦었다. 검색 작업은 일반 약 0.65%, 부족 약 17.2% 증가했다.

90초 일반 관측에서는 원래 성체 식사가 133→102명, 성장 식사가 29→60회, 성장한 주민 식사가 2→16회였다. 추가 성장 식사는 31회로, 기준도 이미 먹은 부분 진행을 제외하면 54회가 아니다. 총소비는 164→178회이고 창고 여유에 따른 실제 생성도 214→228개였다. 부족 공급은 원래 성체 151→80명, 성장 식사 19→60회, 성장 후 식사 0→9회, 총소비 170→149회였다. 부족 공급에서의 초반 손실을 단순한 분배 차이나 탐색 성능 향상으로 표현하지 않는다.

180초 결과는 이 조건에서 원래 성체와 새싹 모두 완료했다는 근거이며, 임의 맵/무한 공급 경쟁에서 영구 기아가 없다는 수학적 증명은 아니다. 총공급·예산·속도를 늘려 기준을 맞추지 않았다.
