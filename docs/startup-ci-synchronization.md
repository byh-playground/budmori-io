대상은 main `765eb219bce148d2e89cbda6e1667cecb0e434ad`의 CI `40637598188`에서 실패한 두 테스트입니다. 승인된 PR head `f553261e02a9b4bf1985924cab2c6cf23823ed16`와 merge의 파일 트리는 동일합니다. 제품 코드·모델·렌더러·저장 형식·제품 버전은 변경하지 않습니다.

## 권위 snapshot 비교

`unit-sprites.e2e.mjs`는 앱 RAF를 중단하기 위해 다음 RAF 예약을 막고 80ms를 기다린 뒤, 수동 시계 1,000,000ms와 고정 seed731로 모델을 진행했습니다. 이미 예약된 앱 RAF가 80ms 뒤에도 실행되지 않았으면 수동 진행 도중 실제 wall clock이 혼입될 수 있었습니다.

CI와 동일한 두 hash를 로컬 SwiftShader에서 재현하고 원본 snapshot과 pulse 추적을 확보했습니다.

| 경로       | 실제 pulse 일부                                    | 마지막 tick / time       | SHA256                                                             |
| ---------- | -------------------------------------------------- | ------------------------ | ------------------------------------------------------------------ |
| 벡터       | 1,000,000 → 1,000,050 → 1,000,100ms                | 16 / 0.8000000000000002s | `fcab89270f987d359472955897f9092867ebcb4f6834e41034351567c42917bc` |
| 스프라이트 | 1,000,000 → **10,467.9** → 1,000,050 → 1,000,100ms | 15 / 0.7500000000000001s | `a719cd36d0ba359a2d22be084b7e785b1183cadf43ab08e26d740cdce243b164` |

마지막 snapshot의 140개 필드 차이는 한 논리 step 차이로 설명되는 위치·속도·나이 등이었습니다. 해당 CI의 화질 46케이스, camera 일치와 render snapshot 불변 검사는 통과했습니다.

수정은 임의 80ms timer 대신 원래 RAF 함수의 다음 callback을 기다리는 것입니다. 다음 RAF 예약을 막은 뒤 원래 함수로 등록한 callback은 기존 앱 callback 다음에 실행되므로, 앱 frame이 완료된 후 모델을 reset하고 수동 시계를 시작합니다. 수동 구간에 앱 wall clock이 들어오면 새 assertion이 실패합니다. 기존 전체 모델 hash 일치 assertion·표본·seed·시뮬레이션 step 크기는 그대로입니다. 실패 시 추적할 수 있도록 기능 검사의 clock trace와 두 전체 권위 snapshot을 artifact에 저장합니다. 성능 벤치 경로에는 pulse 추적 wrapper를 설치하지 않습니다.

수정 후 동일 20개체 기능 검사에서 두 경로 모두 tick16 / 0.8000000000000002s, 같은 `fcab8927…` hash로 통과했습니다. 수동 pulse는 각17회였으며 잘못된 시계 주입은 0회였습니다. 성공 재실행만으로 결론낸 것이 아니라 실패 clock sequence와 원본 snapshot의 차이를 재현한 뒤 원인을 차단했습니다.

## 저장 후 reload

`progress survives a reload`는 reload 후 고정4초만 기다리고 `BUDMORI`를 읽었습니다. 비동기 초기 준비가 더 길면 `ReferenceError: BUDMORI is not defined`로 저장값 assertion 이전에 실패했습니다.

이제 실제 `BUDMORI` 생성과 로딩 overlay 제거를 기다립니다. 회귀에서는 게임 모듈 응답을 실제로 4.1초 이상 보류해 초기화 미완료와 로딩 화면을 확인한 뒤, 응답을 풀고 같은 저장된 `towerBest >= 4` 조건을 검증합니다. 저장값 요구나 실패 기준을 낮추지 않습니다.
